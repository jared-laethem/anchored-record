Section 1

Purpose & threat model

Generative AI is erasing the gap between genuine and fabricated evidence. Within our lifetimes it will be possible to produce video, audio, photographs, and documents of events that never happened — indistinguishable from the real thing by inspection. Over long time spans, motivated actors can use that capability to launder preferred narratives into the historical record, and a society with no way to tell original evidence from later fabrication slowly loses its history.

The Anchored Record is a defense built on one observation: a forgery can be made indistinguishable from the original, but it cannot be made older than the original. If the genuine artifact's cryptographic fingerprint is locked into a public, unrewritable ledger today, then any competing "evidence" fabricated in 2040 arrives provably 14 years late. The registry does not decide what is true; it makes when a thing existed, and who stood behind it permanent facts that no future actor can quietly revise.

The adversaries we design against:

  • Future fabrication — synthetic artifacts created after the fact to support an alternative narrative.
  • Silent alteration — edits to genuine archives (a frame removed, a caption changed) that no one can later detect.
  • Institutional capture — a government, platform, or even the registry's own operators attempting to rewrite or censor entries.
  • Technological decay — cryptographic algorithms weakening, host blockchains dying, and file formats rotting over a 100-year horizon.

Section 2

What the system proves — and what it doesn't

A blockchain can make a statement permanent; it cannot make a statement true. A fabricated photo registered on-chain is still fabricated — it is merely provably old fabrication. This is the central honesty constraint of the whole project, and the design embraces it by splitting trust into three layers:

  • Integrity layer (cryptographic). Content fingerprints anchored in an unrewritable ledger. Proves: this exact sequence of bytes existed no later than date X and has not changed since. Machine-checkable by anyone, forever.
  • Provenance layer (cryptographic + procedural). Signed capture and custody metadata — for new content, hardware-signed at the moment of capture (the C2PA standard); for historical content, the holding archive's accession trail. Proves: this is where the artifact came from and how it traveled.
  • Attestation layer (social, made permanent). Named institutions and individuals cryptographically endorsing artifacts, staking their reputations. Truth emerges from an accountable web of signatures — not from the registry declaring it.
The formal claim, for a historical artifact "This exact file existed no later than 2026, has not been altered since, and these named institutions attest — on evidence they cite and sign — that it was created on September 11, 2001."

The first clause is mathematics. The last clause is testimony, made permanent and accountable. Keeping that line crisp — never presenting testimony as proof — is what makes the registry credible enough to matter.

Section 3

A working mental model of blockchains

This section builds, from zero, exactly the concepts the rest of the document uses. There are only four: hashes, chained blocks, proof of work, and Merkle trees.

3.1 — A hash is a fingerprint for bytes

A cryptographic hash function (we'll use SHA-256, the one Bitcoin uses) takes any input — a sentence, a 4 GB video — and produces a fixed-size 32-byte fingerprint. The same input always gives the same fingerprint. Change anything about the input and the fingerprint changes completely and unpredictably. These two sentences differ by a single digit:

sha256("The first tower fell at 9:59 a.m.")
7e19731e2654c2d902e06886a477037fc31296a99e19dfed16bec4d5739d7229
sha256("The first tower fell at 9:58 a.m.")
595d2f040411a32c99b0f4b026117727ad64c97d2c45f30ff5be84616a72d33a

Two properties matter for us. One-way: given a fingerprint, you cannot reconstruct the input — so publishing a hash reveals nothing about the document. Binding: nobody can find a different input that produces the same fingerprint (Section 8 examines how confident we can be in that over a century). Together they mean: if you hold a fingerprint from 2026 and someone hands you a file in 2080, recomputing the hash tells you with certainty whether it is the identical, unaltered file.

In plain terms

A hash is like a wax seal that any copy of the document can regenerate. You can't reverse the seal back into the document, and no altered document can fake the seal — but anyone holding the real document can re-press the seal and check it matches.

3.2 — A blockchain is a ledger where each page seals the page before it

A blockchain is an append-only ledger, replicated across thousands of independent computers ("nodes"), organized into batches called blocks. The trick that makes it tamper-evident: every block contains the hash of the previous block. Block 900,002 includes the fingerprint of block 900,001, which includes the fingerprint of 900,000, and so on back to the beginning. Alter one character in an old block and its hash changes; that breaks the pointer in the next block, whose hash therefore changes too, cascading forward through every subsequent block. You cannot quietly edit history — you can only visibly rewrite everything after your edit.

3.3 — Proof of work makes the rewrite unaffordable

Tamper-evidence isn't enough; you also need rewriting to be practically impossible. Bitcoin's answer: to add a block, a computer must win a brute-force lottery — trying quadrillions of guesses until it finds a number that makes the block's hash fall below a target. This is "mining," and the network's combined guessing rate is currently on the order of 10²⁰–10²¹ hashes per second. Each block therefore embodies an enormous quantity of provably-performed computation, and every node independently follows one rule: the valid chain with the most cumulative work is the real one.

To alter a transaction buried 1,000 blocks deep, an attacker must re-mine that block and all 1,000 after it, and do so faster than the entire honest network extends the chain — meaning they must sustainably out-compute every miner on earth combined. Sixteen years and trillions of dollars of incentive have not produced a single successful rewrite of settled Bitcoin history. That accumulated, verified expenditure of energy is the product we are buying when we anchor: we rent the security of the most attacked ledger in existence for the cost of one small transaction.

Why we don't run our own proof of work

Security scales with honest computing power. A new, small proof-of-work chain can be overwhelmed with rented hashpower for a few thousand dollars — dozens of small chains have been attacked exactly this way. For a project whose entire premise is "history cannot be rewritten," launching with weak security would be self-defeating. Section 5 describes what our network uses instead.

3.4 — Merkle trees: a million records in one fingerprint

Writing to Bitcoin costs a fee per transaction, and a transaction can carry only ~80 bytes of arbitrary data. That is not a limitation for us, because of a structure called a Merkle tree: take a million record hashes, pair them up and hash each pair, pair up those results and hash again, and repeat until a single 32-byte root remains. The root provably commits to every record beneath it — change any one record and the root changes.

The counterintuitive gift is verification cost. To prove one specific record is in the tree, you don't need the other 999,999 — you need only the ~20 "sibling" hashes along the path from your record up to the root (log₂ of a million). That handful of hashes is called a Merkle proof, it's under a kilobyte, and anyone can check it in microseconds. So: unlimited records in, one 32-byte anchor out, and every individual record independently provable. Figure 2 draws it.

3.5 — Documents never go on the chain

Nothing about the files themselves — not content, not thumbnails — is ever published to any blockchain. Only fingerprints and signed metadata. This keeps costs trivial, keeps copyrighted and sensitive material out of scope (a hash of a copyrighted work carries no copyright), and means registering a document reveals nothing about it until its holder chooses to produce it.

Section 4

The anchoring mechanism, end to end

This is the mechanistic core of the design. We follow one artifact — say, a broadcast master tape of September 11 coverage, digitized by its holding archive — from a file on a curator's disk to a permanent, independently verifiable anchor in Bitcoin, and then forward fifty years to the person verifying it.

Hash locally — the file never leaves the archive

The curator runs our tool against the digitized file. It computes two fingerprints under independent algorithms (SHA-256 and SHA3-256 — Section 8 explains why two) on the archive's own machine. Nothing is uploaded. For a 50 GB master file this takes a couple of minutes; for a million-file collection it's an overnight batch job.

Submit a signed record to the registry ledger

The tool assembles a record — the fingerprints plus the metadata of Section 9 (asserted creation date, provenance references, content description) — and signs it with the archive's registered cryptographic key, so the submission is unforgeably attributable. The record goes to the registry network (our consortium ledger, Section 5), whose nodes validate the signature and format and write it into the next ledger block. At this point the record is replicated across every consortium institution, but not yet anchored.

The epoch closes; records are batched into a Merkle tree

On a fixed cadence — say hourly — the ledger closes an epoch: every record accepted since the last close becomes the leaves of a Merkle tree, computed identically and deterministically by every node. One epoch might hold ten records or ten million; either way it reduces to one 32-byte root. Batching is why our marginal cost per record is effectively zero.

The root is anchored into Bitcoin (and Ethereum)

Now the part that makes the history unrewritable. Bitcoin transactions can carry a small arbitrary-data field (an OP_RETURN output, up to 80 bytes). The registry constructs an ordinary transaction — from our own wallet, paying a normal fee of a few dollars — whose data field is the epoch root, and broadcasts it to the Bitcoin network like any other payment.

Here is the crucial mechanistic point about working on someone else's network: we need no permission, no partnership, and no special status. Miners neither know nor care what our 80 bytes mean; they include the transaction because it pays a fee, exactly as they include millions of others. Within ~10 minutes it is mined into a block; after ~6 further blocks (~1 hour) it is buried under enough proof of work that reversal is considered practically impossible. Our root now sits inside the chained-and-sealed structure of Section 3.2, protected by the full mining power of the network — which is defending its own monetary history and ours as an inseparable side effect.

For redundancy against the death or capture of any single chain, the same root is also written to Ethereum (as an event in a small contract) and can be cheaply mirrored to others. The anchors are independent; any one surviving suffices.

Receipts: every record gets a portable proof

Once the anchor transaction is confirmed, the ledger stores — and hands back to the registrant — a receipt: the record's Merkle proof (the ~20 sibling hashes up to the epoch root) plus the identifiers of the anchor transactions and blocks. The receipt is under a kilobyte, is not secret, and is self-contained: it will let anyone, forever, verify this one record against the public blockchains without contacting us. Registrants are encouraged to store receipts alongside the files themselves.

Verification, fifty years later

2076. Someone produces a video file and claims it is the anchored 2026 broadcast master. A skeptic — with no trust in us, and even if our organization no longer exists — checks it as follows:

  1. Recompute the file's SHA-256 and SHA3-256. If either differs from the record, the file is not the anchored artifact. Done.
  2. Replay the Merkle proof: hash the record with its ~20 siblings, arriving at an epoch root.
  3. Confirm that root sits in the referenced Bitcoin block — using any copy of the Bitcoin blockchain, of which thousands exist worldwide — and that the block sits under the chain's accumulated proof of work.

Every step is arithmetic on public data. The full Bitcoin block-header chain — sufficient for step 3 — grows about 4 MB per year; a century of it fits on any device. This is the property the whole design serves: verification requires no institution, no server, and no permission — only the file, a kilobyte receipt, and public data.

Prior art: this pipeline already exists

The mechanism in steps 3–5 is precisely the design of OpenTimestamps (Peter Todd, 2016): calendar servers Merkle-aggregate unlimited submissions into roughly one Bitcoin transaction an hour, free, with self-contained receipts verifiable offline forever. Its 2017 anchoring of ~750 million Internet Archive files in a single transaction proved the mass-ingestion math in production. We adopt its proof format and aggregation design — running our own consortium calendar server rather than relying on today's donation-funded, essentially one-maintainer public infrastructure — instead of reinventing this layer. See Section 12.

Costs and dependencies of riding an existing network

  • Cost. One transaction per epoch per chain. Hourly anchoring to Bitcoin and Ethereum runs to roughly $50–100/day at typical fees — independent of volume, whether the epoch holds one record or ten million.
  • No counterparty. There is no contract with "Bitcoin"; there is nothing to negotiate and no one who can cancel us. The flip side: no support and no guarantees beyond the protocol itself.
  • Fee volatility. Fees fluctuate with network demand. Because we write ~24 transactions a day rather than one per record, even a 100× fee spike is an operational nuisance, not an existential problem.
  • Censorship. Miners could theoretically refuse our transactions; because any miner anywhere can include them and they look like ordinary payments, sustained global censorship is considered impractical.
  • Host-chain death. If a host chain declines, its existing anchors remain checkable so long as copies of its data survive (a dead chain's history still verifies; it just stops growing). We mitigate with multi-chain anchoring, and a standing procedure: if a host weakens, anchor the registry's full state onto its successor before the decline — the old anchors then prove the migration itself predates any trouble.

Section 5

Our network: the registry ledger

Bitcoin gives us unrewritability but only 80 bytes an hour. The registry itself — full records, metadata, attestations, receipts — lives on our own ledger, and its design goal is different: not to win a security arms race (the anchors handle that), but to be rich, replicated, and governable.

Proof of authority: known signers instead of anonymous miners

Proof of work exists to order transactions among strangers. Our block producers are not strangers: they are named institutions — archives, libraries, universities, news organizations — each running a node and holding a signing key. A ledger block is valid when co-signed by a supermajority (e.g., two-thirds) of members. This is "proof of authority": no energy expenditure, high throughput, and accountability — a misbehaving signer is identifiable and expellable, the opposite of anonymous mining.

Its classic weakness is that the authorities could collude to rewrite history. The anchors neutralize exactly that: any rewrite of anchored epochs would produce roots that fail to match what is buried in Bitcoin, visibly and provably. Collusion can only affect the un-anchored last hour — which is why the anchoring cadence is a security parameter, not a convenience. There is 25 years of precedent for institutions cooperating this way: LOCKSS ("Lots of Copies Keep Stuff Safe") has had libraries jointly preserving digital content since 1999, and CLOCKSS runs 12 archive nodes worldwide under a governance board split evenly between libraries and publishers. More pointedly, the exact architecture proposed here has been field-trialled: ARCHANGEL (2017–19) ran a proof-of-authority ledger jointly operated by the national archives of the UK, Estonia, Norway, Australia, and the US, each underwriting the others' records. It worked; what it lacked was a sustaining institution after the research grant ended (Section 12).

Storage: every node holds everything, forever

A record is roughly 1 KB (two hashes, signatures, metadata). One billion records ≈ 1 TB — a $40 disk. Bitcoin's entire 16-year chain is ~600 GB. Full replication at every member node is therefore trivially affordable and is exactly what an archival mission wants: dozens of complete, independently held copies across jurisdictions. The ledger is public — anyone, member or not, may read it, mirror it in full, and serve verification from their copy. The consortium controls writing; nobody controls reading.

Membership and governance (to be developed)

  • Joining: admission of a new member (charter criteria + supermajority vote), a key ceremony, and a node bootstrapped from existing copies.
  • Leaving / expulsion: keys retired on-ledger; past signatures remain valid for the blocks they signed. Departure never invalidates history.
  • Diversity requirement: members spread across countries and legal systems, so no single government can compel a quorum.
  • Funding: a patronage-endowment model — sponsors fund the anchoring of specific corpora and institutions, and the endowment pays archives to ingest rather than charging them (Section 13). Operations are cheap (nodes + ~$100/day of anchoring). Deliberately no token — see Sections 11 and 13.

Section 6

Time: anchored vs. asserted dates

Every record carries two dates, and the system's credibility depends on never blurring them:

  • Anchored date proven — when the record entered the ledger and was buried in Bitcoin. Machine-generated, never editable, never backdated, under any circumstances. This is the only date the mathematics stands behind.
  • Asserted creation date asserted — when the registrant claims the artifact was created, carried as signed metadata with cited evidence (accession records, broadcast logs, publication dates) and whatever attestations support it. Testimony — permanent and accountable testimony, but testimony.

Allowing even one backdated chain entry would convert every timestamp in the system from proof into testimony. The rule is absolute; the schema makes misrepresentation structurally impossible by generating the anchored date from the anchoring process itself.

Section 7

Identity & attestations

The integrity layer answers "is this unaltered and how old is it." Attestations answer "why should I believe it's what it claims to be." An attestation is a small signed statement, itself a ledger record (and therefore anchored): identity X, in role Y, states Z about record R, on evidence E.

  • Identities are cryptographic keys bound to named entities — primarily institutions at first, whose reputations are the collateral. The registry maintains an identity ledger: key issuance, rotation, and revocation are themselves anchored records, so "who was authorized to speak for the AP in 2026" is permanently answerable.
  • Roles are typed, not freeform: originating archive, digitizer, independent holder of a matching copy, eyewitness, publication of record. A record's credibility is legible from who signed in which role.
  • Corrections are append-only. If an attestation proves wrong — or an artifact is exposed as fake — nothing is deleted. A superseding record, signed and anchored, marks the correction. The registry's own mistakes become part of the permanent record; that is a feature, and the only honest option for a system that forbids rewriting.
  • Post-quantum signatures. Unlike hashes, today's signature schemes (ECDSA, Ed25519) will fall to quantum computers. Attestations are therefore dual-signed — a classical scheme plus a NIST post-quantum scheme (e.g., ML-DSA) — from early on. And because every signature is anchored, even a future forgery of an old key fails: the forged attestation would carry a post-break anchor date.
  • Candidate substrate. Starling Lab's open-source Authenticated Attributes — an append-only database of individually signed, timestamped claims keyed to media hashes, with selective disclosure — implements much of this layer already and has been exercised in legal-grade casework (Section 12). Evaluate building on it before writing anything new.

Section 8

Hash durability over a century

Could a future supercomputer craft a different document — one that distorts the facts — with the same fingerprint as an anchored original? Three separate threats, three separate answers:

Brute force: no

Finding a second input matching a given SHA-256 hash requires on the order of 2²⁵⁶ attempts. This is not "a very big computer" territory: a computer converting the sun's entire power output into hashing at theoretical thermodynamic limits would not get there in the sun's remaining lifetime. Brute force is off the table permanently, not provisionally.

Quantum computers: no

Grover's algorithm — the best known quantum attack on hashing — only square-roots the work: 2²⁵⁶ becomes 2¹²⁸, still hopelessly out of reach. Hashes are the most quantum-resistant component in the system (signatures are the vulnerable part, handled in Section 7).

Cryptanalytic breaks: the real risk, managed two ways

MD5 and SHA-1 were once trusted and later fell — this is the honest historical worry. But note what "fell" means: they fell to collision attacks, where the attacker crafts two documents together, before either is published. Our threat is different. The genuine artifact is already anchored; its hash is fixed. The forger needs a second preimage — a new document matching an existing hash — a categorically harder problem. Even MD5, broken for collisions since 2004, has no practical second-preimage attack two decades later. And the forgery would need to be simultaneously byte-level hash-matching and a coherent video advancing a specific false narrative — constraints that fight each other.

We still refuse to bet a century on any single algorithm:

  • Dual hashing. Every record carries SHA-256 and SHA3-256 — algorithms with unrelated internal designs. A viable forgery must defeat both at once.
  • Hash agility as procedure. Cryptanalytic declines announce themselves years in advance (SHA-1: theoretical weakness 2005, first real collision 2017). When a successor standard matures or an incumbent shows strain, the corpus is re-hashed under the new algorithm and the mapping is anchored. The old anchors then prove the re-hashing happened before any break — so the chain of integrity never lapses. The system is future-proofed by standing procedure, not by hoping an algorithm holds.
A practical boundary to hold

A cryptographic hash authenticates exact bytes. Re-encode a video or screenshot a photo and the hash changes completely — so copies circulating on social platforms will not match the anchored canonical file. Perceptual fingerprints ("this looks like that") can be stored as advisory metadata to help people find the canonical record, but they are never proof, and the registry must say so plainly.

Preservation without custody: the hash is the address

A registry of hashes has an obvious dependency: a fingerprint is only useful while someone, somewhere, still holds a matching file. If the last copy disappears — or merely gets re-encoded everywhere — the anchor points at nothing. The registry never takes custody of files, but it can make their survival dramatically more likely, because of a property of peer-to-peer networks that fits this design like a glove: on content-addressed networks, the hash is the address.

On IPFS, a file's identifier (its CID) is derived from its content; on BitTorrent, a magnet link is the hash of the torrent's contents. The address doesn't say where the file lives — it says what the file is, and the network locates anyone currently holding matching bytes. Three consequences:

  • Moving cannot break the link. There is no server to die and no URL to rot; as long as anyone on earth hosts the file, the address in the record resolves.
  • Retrieval is self-verifying. Whatever the network returns is checked against the address itself — a tampered file cannot be served at a content address, so fetching and verifying collapse into one act.
  • Preservation is permissionless and additive. Anyone can start hosting a registered file at any time, forever, and the record's address needs no update — the same "separable and later-attachable" property the design exploits for attestation.

The honest limitation, kept crisp because many projects fudge it: a content address is permanent; the content's availability is not. IPFS is a naming system over volunteers, not a hard drive in the sky — bytes persist only while someone "pins" (hosts) them. So permanence decomposes into a permanent address (free, automatic) plus an ongoing commitment to hold bytes, and the registry leans on three compatible mechanisms for the second half:

  • Institutional pinning — the primary mechanism. Consortium members pin one another's registered public-domain corpora: LOCKSS's founding principle ("lots of copies keep stuff safe") ported to content addressing, and folded into the mutual-underwriting obligation of Section 13 — members countersign and co-host. Storage at these scales is a rounding error for a university library.
  • Paid-permanence networks. Filecoin (renewable storage deals with on-chain proofs the host still holds the data — where Starling Lab keeps the Shoah testimony archive) and Arweave (a one-time payment into a storage endowment) let a patron gift buy hosting permanence, not just anchoring.
  • BitTorrent for the iconic. Twenty-plus years of demonstrated survival for anything the public cares about, at zero institutional cost.

Scope boundaries: this applies in full only to material that may lawfully be redistributed (public domain and licensed collections); copyrighted holdings stay hash-plus-custodian as designed, with the content address recorded anyway — dormant — so preservation can attach to the existing record the day the material enters the public domain. And content addressing does not touch the re-encoding problem (open question 4): a transcode is genuinely different bytes, handled as a related record. It helps only at the margin — when the canonical file is always fetchable at a permanent address, the world has less reason to circulate lossy copies at all.

Section 10

Seeding the historical record

Retroactive ingestion is a race against time: every year before an artifact is anchored widens the window a future fabrication can exploit (Figure 4). Nothing can produce a cryptographic proof of 2001 for a 2001 tape — the moment of capture is gone — but anchoring it now, with institutional attestation, beats every fake made afterward. The wall moves only forward.

Induction workflow

The holding institution hashes its own files in place (nothing uploaded), signs the batch with its provenance evidence, and submits; the consortium validates and anchors. The institution's attestation is the trust; the anchor makes it permanent. A million-file collection is one overnight hashing job and a few epochs of ledger writes.

Candidate first corpora

  • Internet Archive — the September 11 Television Archive. Continuous off-air recordings of 20 networks from that week: historically critical, heavily conspiracy-targeted, already digital, held by a mission-aligned nonprofit. The natural pilot.
  • Vanderbilt Television News Archive — systematic U.S. broadcast news recording back to 1968.
  • National archives (NARA and international counterparts) and the Library of Congress.
  • Wire services — AP and Reuters photo/video archives.
  • Court records, university special collections, Wikimedia Commons.

The pilot doubles as consortium recruitment: the first corpora's holders are exactly the institutions we want operating nodes.

Why the moment favors this (2026)

  • The convening exists. The Library of Congress launched a content-authenticity community of practice for libraries, archives & museums in July 2025; its 2026 white paper calls on the sector to make collections verifiable in the AI era. That community — not any single archive's front door — is where this proposal should land.
  • The pilot is easier than it looks. The Internet Archive already publishes per-file hashes for its holdings — unsigned and unanchored. The pilot proposal is nearly "sign and anchor what you already publish."
  • Courts have named the gap. In Weinhoffer v. Davie Shoring (5th Cir. 2022), a federal appeals court held Wayback Machine captures are not self-authenticating — institutional custody alone no longer satisfies; anchored, signed attestation is precisely the upgrade the ruling implies.

Section 11

Deliberate non-goals

  • No file custody — but preservation-aware. The registry holds fingerprints and content addresses, never content — sidestepping IP ownership entirely and keeping records ~1 KB. Preservation of the files themselves remains the archives' mission (LOCKSS, Internet Archive, institutional repositories), reinforced by the content-addressing and pinning mechanisms of Section 9: the registry points permanently at the bytes and organizes others to hold them, without ever holding them itself.
  • No truth adjudication. The registry never rules on what happened. It makes existence-dates provable and testimony permanent and attributable; judgment belongs to readers, historians, and courts.
  • No token. A native token would make the attestation layer purchasable — influence flowing to whoever buys the most — in exactly the domain where neutrality is the product. Our securers are named institutions with mission alignment; funding is patronage, dues, and earned certification revenue (Section 13, including the full case against a coin). (Hence also: the working directory name "record_coin" has outlived the design.)
  • No similarity-based authentication. Perceptual matching is discovery metadata only. The registry's proofs are exact-bytes or nothing, stated plainly.

Section 12

Prior art & positioning

A full survey — a 35-year timeline, a capability matrix of fifteen systems, and sources for every claim — lives in the companion document, The Provenance Landscape (September 2026). Its conclusions, condensed:

  • The anchoring layer is solved. OpenTimestamps has provided free, unlimited-scale Bitcoin anchoring since 2016 and demonstrated 750-million-file retroactive ingestion in 2017. We build on it (Section 4), running our own calendar infrastructure.
  • The capture-provenance layer is industry-crowded and leaky. C2PA ships in real cameras and AI generators, but manifests are stripped by essentially every social platform, recovery is centralized in Adobe's cloud, its trust model is a corporate conformance allowlist, and it has no model for pre-C2PA historical material. Our registry sits above C2PA — ingesting its manifests as one input class — not against it.
  • The two layers this project actually consists of are unbuilt. No public registry of institutional attestations over the historical record exists anywhere, and no provenance system has century-scale governance. The nearest technical relative, Starling Lab (Stanford/USC), has validated our full stack — multi-chain hash anchoring, signed attestations on hashes, even multi-institution corroboration prototypes — but at curated case-study scale (its flagship retro-authentication project sealed 131 photos), with no open registry and grant-dependent permanence. It is a natural founding partner, not a competitor.
  • The direct precedent is a ghost. ARCHANGEL (2017–19) trialled our precise consortium architecture across five national archives, succeeded technically, and dissolved when its grant ended — for organizational reasons, not cryptographic ones. Its post-mortem is required reading before any institutional pitch, and its participants are warm leads.
  • The graveyard's lesson is the design brief. Every operator-dependent system decayed: Surety flickering after 30 years of valid proofs, Guardtime (Estonia's national ledger operator) down to ~1 employee, Stampery's verification portal a dead URL, Tierion and Factom broken on token economics. Proofs outlived every operator. The survivable pattern — consortium stewardship, self-contained proofs verifiable without any live service, public-chain anchoring as operator-independent backstop, planned algorithm renewal — has never been combined in one system. That combination is this project.
  • Law has moved toward us. eIDAS 2.0 (EU, 2024) created "qualified electronic ledgers" with legal presumption of chronology and integrity — the first regulatory template for this architecture; China's courts presume anchored evidence untampered post-anchoring while demanding separate proof of pre-anchoring authenticity (exactly our proven/asserted split); several US states have admissibility statutes. Qualified-ledger status is worth designing toward.

Positioning, in one sentence: the Anchored Record is not a new protocol but a missing institution — the consortium-governed attestation registry that ARCHANGEL prototyped, Starling's tooling enables, the Library of Congress community is newly convened to want, and no one has yet built to last a century.

Section 13

Incentives & sustainability

The prior-art graveyard has one consistent cause of death: the people who had to do the work got nothing they valued for doing it. ARCHANGEL's archives got a research paper; ACE's subscribers got a mailing list; token-funded ventures got securities actions. This section is the design against that failure mode. The settled model is patronage: deep-pocketed individuals and organizations fund the anchoring of specific archives and collections, and every other incentive is built around that spine.

The patron model: sponsor a corpus

The core giving product is naming-rights economics applied to memory. A patron funds the ingestion and perpetual anchoring of a named collection — "The September 11 Television Archive, anchored in perpetuity by the ___ Foundation" — and, for redistributable collections, its perpetual hosting as well (Arweave/Filecoin permanence plus consortium pinning, Section 9): anchored and replicated, in one gift. The sponsorship itself becomes a signed, anchored record in the ledger: permanent, public credit beside the history it preserved. Patronage has two properties most philanthropy lacks:

  • Permanence per dollar. A one-time gift anchors a corpus forever. There is no ongoing burn to sustain the impact — the anchors are already immortal; the endowment only funds new ingestion and node operations.
  • Legible, bounded asks. "Fund the anchoring of the Apollo program archive" is a concrete, completable, emotionally resonant project — the shape of gift that built every named library wing in existence — rather than an open-ended operating subsidy.

Solicitation targets, in order of fit: foundations already funding information integrity and AI-risk work; crypto-ecosystem philanthropy with a track record in this exact niche (the Filecoin Foundation gave the Internet Archive $10M; Protocol Labs bankrolls Starling Lab; retroactive public-goods programs fund open infrastructure); AI companies, whose reputational need for provenance infrastructure is acute and growing; and individual patrons for whom permanent named association with preserved history is the draw.

What each participant gets

  • Archives & libraries — trust insurance, revenue, and prestige. Post-Weinhoffer, institutional custody alone no longer satisfies courts; anchored attestation makes holdings self-authenticating again — insurance for the archive's core asset, its authority. Joining is engineered to near-zero cost ("sign and anchor what you already publish"), and the endowment pays ingestion bounties for named, vetted collections — archives are paid to participate, never charged. Founding membership confers a permanent, visible role: every future verification of a sponsored corpus displays the attesting institution's name.
  • Patrons — permanent named credit, recorded in the same unrewritable ledger as the history itself.
  • The AI industry — certified pre-AI data. Data created before generative AI is acquiring the status of low-background steel: valuable precisely because it is provably uncontaminated, and an anchor date is the only retroactively unfakeable proof of that. Certifying "verified pre-AI" corpora for model training and evaluation is a genuine earned-revenue line whose buyers have real budgets — and the same anchors serve historians and dataset auditors alike.
  • Members mutually — the network effect. Consortium members countersign one another's holdings and pin what they attest (Section 9): ARCHANGEL's mutual-underwriting idea plus LOCKSS's replication, made a single charter obligation. Each new member adds independent attesters, jurisdictions, and hosted copies to every existing member's collections, so membership value rises with membership — a real network effect, without a token.
  • The public — free verification, forever, plus a visible coverage map ("23% of major broadcast history anchored; these collections are not") that converts the remaining gap into standing public pressure and recurring journalism.

Why not a native coin

The question every crypto-literate reader will ask, considered seriously and answered structurally:

  • Token incentives only work where the rewarded work is machine-verifiable. Bitcoin pays for hashes computed; Filecoin pays for bytes provably held — protocols can check both, so rewards can't corrupt the work. Our scarce input is truthful institutional testimony, which no protocol can verify. Reward what's measurable (records registered) and you invite farming junk hashes for coins; reward what matters (attestation) and you have literally priced testimony — the credibility-for-sale failure this registry exists to fight.
  • The securities precedent is in our own survey. Tierion settled with the SEC and refunded $25M; Factom's token dragged it into liquidation. "Buy coins as an investment in the registry" is close to a textbook unregistered security.
  • A coin repels the essential participants. National archives and university libraries cannot hold speculative assets, and the explanation tax with courts, journalists, and archivists spends the one currency — credibility — the project cannot mint more of.
  • Token treasuries are pro-cyclical — flush in manias, collapsed in winters — the opposite of the endowment behavior a century-scale institution requires.

The crypto world's contribution is welcome as funding and rails — its philanthropy already underwrites this mission's nearest relatives, and its chains are our anchor — but the registry itself issues nothing tradeable.

The inviolable line Money buys service and credit — ingestion, certification, tooling, permanent patron records. Money never buys attestation content. No payment, sponsorship, or membership tier confers any influence over what any institution attests, and the charter makes this unamendable. The moment credibility is purchasable, the registry is a slower version of the problem it fights.

The funding tripod, summarized

  • Patron endowment — sponsor-a-corpus gifts and general endowment; funds operations, node grants, and ingestion bounties.
  • Member dues — modest, CLOCKSS-style, sized as insurance premiums on institutional authority; waived where hardship would exclude a valuable member.
  • Earned revenue — certified pre-AI corpus licensing for the AI industry; authenticated-evidence services for courts and publishers. Grows with exactly the forces (AI proliferation) that grow the mission's urgency.

Section 14

Build-out plan

The sequencing principle comes from a fact the architecture makes available: anchoring and attestation are separable, and only anchoring is a race. An anchor must exist before the fakes do; an institution's signed attestation can attach to an already-anchored hash years later, and the early anchor date still holds. Anchoring public content requires no one's permission — a single operator demonstrably can do it at hundreds-of-millions-of-files scale (Todd, 2017). So the plan front-loads everything that can be done unilaterally, and approaches institutions with a running system rather than a proposal. Every ARCHANGEL archive joined a proposal that then needed them to survive; this plan inverts that.

Phase 0 — Prime the pump (solo; no partners required)

  1. Anchor the project itself. OpenTimestamps-anchor this repository and document history. Trivial effort; teaches the toolchain end to end; the project's own provenance becomes its first anchored record.
  2. Build the ingestion pipeline, dogfooding the schema. A tool that takes a directory, computes SHA-256 + SHA3-256, assembles Section-9 records (asserted dates, provenance notes, registrant signature), Merkle-batches, anchors via OpenTimestamps, and emits self-contained receipts. This is both the prototype of the real system and the instrument for everything below.
  3. Anchor a fully public, downloadable, iconic corpus. Lead candidate: NASA's Apollo program archive — public domain, hosted for download by NASA, and heavily conspiracy-targeted, so the demonstration lands. Alternates/additions: Library of Congress digital collections, NARA's catalog, Wikimedia Commons featured media. Stated honestly as third-party registration ("these exact files, as NASA published them, existed unaltered as of 2026"), not custodial attestation — the part that cannot be done later, done now. Being public domain, the corpus is also pinned to IPFS, seeded on BitTorrent, and (patron permitting) written to Arweave — making the pilot a complete demonstration: anchored, addressed, and hosted, by one operator, permission from no one.
  4. Ship the public verify page. Drag a file and a receipt onto a static page; green or red; works offline. The ten-second demo that makes the idea legible to a patron or an archive director.
  5. Publish the coverage map. The major historical corpora, anchored vs. not — almost everything "not." Advocacy artifact, recurring-journalism bait, and the frame that makes each new anchor a visible filled-in square.
  6. Anchor the Internet Archive's published metadata. IA publishes per-file hashes through its public API; anchoring those manifests fences the claimed contents of restricted collections (the September 11 Television Archive included) behind the wall at zero cost — a weaker guarantee (self-reported, older algorithms), held honestly as such, while the custodial pilot is courted.

Phase 1 — First partners (one institution, one patron)

  1. The ARCHANGEL post-mortem (open question 1) — before any pitch, learn why five national archives let a working trial lapse; its participants are also warm leads.
  2. Court Starling Lab as founding technical partner; evaluate Authenticated Attributes as the attestation substrate (Section 7).
  3. Enter through the Library of Congress G+LAM community with Phase 0 in hand: live pipeline, anchored Apollo corpus, verify page, coverage map.
  4. Convert the IA relationship: from anchored-manifests (Phase 0.6) to the real custodial pilot — IA signs and anchors what it already publishes; the September 11 Television Archive becomes the first attested corpus.
  5. Land the first patron against a named corpus, using the prospectus distilled from Sections 13–14.

Phase 2 — Consortium formation

  1. Charter (admission, quorum, jurisdictional spread, the inviolable line of Section 13), legal entity, and the first 5–10 member institutions operating nodes.
  2. Migrate from OpenTimestamps-only anchoring to the full consortium ledger of Section 5, with Ethereum as the second anchor chain; all Phase 0–1 receipts carry forward unchanged.
  3. Mutual underwriting begins: members countersign one another's holdings; the network effect starts compounding.
  4. Begin the eIDAS 2.0 qualified-ledger assessment (open question 6).

Phase 3 — Scale

  1. Mass ingestion bounty program across national archives, broadcast archives, and wire services.
  2. Launch pre-AI corpus certification for the AI industry (Section 13) — the earned-revenue engine.
  3. Individual-registrant on-ramps (open question 5), C2PA manifest ingestion as a standing input class, and endowment campaign to century-scale sizing.

Phase 0 is deliberately buildable by one or two people. Its output is not a demo for its own sake — every receipt it produces remains valid in the final system, and every month of delay is a month of anchor dates lost.

Section 15

Open questions

  1. Governance capture — and governance survival. Charter design: admission criteria, quorum rules, jurisdictional distribution, and what happens if a majority of members are compelled or corrupted. The anchors protect the past; governance protects the future. First research task: the ARCHANGEL post-mortem — why did five national archives that successfully trialled this architecture let it lapse, and what (budget line, legal entity, mandate) would have made them continue?
  2. Attestation trust UX. How does a skeptical citizen in 2080 read a web of institutional signatures without simply being told "trust these institutions"? Reputation surfacing, competing attestations, and dispute records need design.
  3. Verification experience. The cryptography allows trustless verification; the tooling must make it a one-click act for a non-technical person, including offline.
  4. The canonical-file problem. Most people encounter re-encoded copies that won't hash-match. What's the path from "a copy in my feed" to "the anchored canonical record"?
  5. Individual registrants. V1 is institutional. When and how do individuals (journalists, eyewitnesses) register content, and how is spam/poisoning of the ledger priced out without excluding the powerless?
  6. Legal standing. What would it take for anchored records and receipts to be recognized as evidence of date-of-existence in court? Concretely: is eIDAS 2.0 "qualified electronic ledger" certification achievable for a consortium ledger, and what would it require of the operators? No court has yet accepted an OpenTimestamps-style proof by name — a first-mover opportunity for a well-run registry.
  7. Funding & permanence. Endowment sizing for a century of operations; successor stewardship if the founding organization dies (the data survives regardless — who keeps operating?).
  8. The name. "The Anchored Record" is a working title.

Section 16

Glossary

Hash
A fixed-size fingerprint (32 bytes here) computed from any input; any change to the input changes it completely. One-way and binding.
Second preimage
A different input matching an existing hash — the forgery our adversary needs, and much harder than a collision (two crafted-together inputs).
Block
A batch of ledger entries that includes the hash of the previous block, chaining history together.
Node
A computer holding a copy of a ledger and validating new blocks.
Miner
A Bitcoin node competing to add the next block by brute-force search; paid in fees and new coins.
Proof of work
Security from provably expended computation; rewriting history means redoing it all, faster than the whole network.
Proof of authority
Security from named, accountable signers; blocks valid when a quorum co-signs.
Confirmation
Each block mined after yours; ~6 confirmations (~1 hour) is Bitcoin's conventional "settled."
Merkle tree / proof
Pairwise hashing that commits millions of records to one 32-byte root; a proof is the ~log₂(n) sibling hashes linking one record to that root.
OP_RETURN
The ~80-byte arbitrary-data field of a Bitcoin transaction; where our epoch roots live.
Anchor
Publishing an epoch's Merkle root into an external chain, renting its unrewritability.
Epoch
The fixed interval (e.g., one hour) of registry records batched under a single anchored root.
C2PA
Industry standard for capture-time provenance — cameras and tools cryptographically signing content at creation.
Content address
A peer-to-peer identifier derived from a file's content (an IPFS CID, a BitTorrent magnet link): it names what the file is rather than where it lives, resolves wherever a copy is hosted, and cannot serve tampered bytes.
Pinning
Committing to keep hosting a file at its content address. Addresses are permanent; availability lasts only as long as someone pins.
